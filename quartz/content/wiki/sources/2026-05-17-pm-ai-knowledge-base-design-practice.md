# 2026-05-17-pm-ai-knowledge-base-design-practice

> 从个人找资料的痛点出发，本文给出一条把本地 RAG 试验升级为可多端访问、可多人协作的云端 AI 知识库产品路径，重点落在技术选型、MVP 取舍、产品信息架构与后续迭代治理。

## 核心观点

1. **知识管理的真正断层不在“存储能力”，而在“语义理解能力”**：作者以“找 AI 在银行客服场景中的应用案例”为例，说明传统文件系统只能匹配文件名，无法理解问题意图。对 20 位知识工作者的非正式调研中，87% 经常找不到已存内容，63% 曾因找不到资料而重复下载或重复整理。
2. **本地 RAG 能验证价值，但天然卡在可用性和协作性上**：Ollama + Dify + 本地模型的组合已经能通过问答从文档中提取内容，但一旦离开电脑就无法访问，也难以让其他成员复用。同一套环境若要求每个成员重复搭建，会把技术门槛转化为产品增长瓶颈。
3. **MVP 阶段的技术选型要优先服务“尽快跑通全链路”**：作者把成本（40%）、可扩展性（25%）、部署维护复杂度（20%）、文档与社区活跃度（15%）作为权重，放弃了 Cherry Studio、MaxKB、WeKnora 等方案，最终选择提供 RESTful API、支持 Docker 三步部署、无调用次数限制的 Yuxi。
4. **知识库产品不该只有“AI 对话框”，而应同时支持快捷检索与智能检索**：作者根据用户习惯设计双模式首页，上半部是关键字快速检索，下半部再接智能助理。这一设计背后的判断是：70% 用户希望在 30 秒内直接浏览或搜索，而不是一上来就对话。
5. **AI 知识库的核心不是“能答”，而是“能落地到组织流程”**：V1.1 功能清单把服务器部署、用户登录、移动端适配、基础问答 API 集成列为 MUST，把文件上传下载、关键词检索列为 SHOULD，把多文档总结和权限分组列为 COULD，说明产品价值要通过多端访问、多人协作和权限治理来兑现。

## 实操内容保留

### 技术选型与部署要点

- 本地试验组合：**Ollama + Dify + Qwen 等本地模型**
- 最终选型：**Yuxi + Docker 部署 + RESTful API + MinIO + Milvus + C#.NET MVC 前后端**
- MVP 技术评估框架：
  1. 成本 40%
  2. 可扩展性 25%
  3. 部署与维护复杂度 20%
  4. 文档与社区活跃度 15%

### 部署步骤（原文结构保留）

1. 安装 Docker Desktop，并配置国内镜像加速。
2. 获取 Yuxi 代码仓库，使用浅克隆 `--depth 1` 降低下载量。
3. 配置环境变量，建议使用脚本方式完成。
4. 启动服务，首次拉取镜像与编译需要等待 2-3 分钟。
5. 访问：
   - Web 界面：http://localhost:5173
   - API 文档：http://localhost:5050/docs
6. 首次访问时设置超级管理员账号密码。

### 原文中的具体工程细节

- 如果 API 返回中文异常，根因是**后端 API 默认 ASCII 编码不支持中文**，需修改编码配置后再重试。
- Yuxi 问答接口支持**流式输出**，返回是一个个 JSON 片段；当 `status="loading"` 时程序持续读取，直到 `status="finished"` 再结束前端展示。
- 后端职责包括：
  - 用户认证（Session + JWT）
  - 调用 Yuxi API 完成问答并流式转发给前端
  - 对接 MinIO 实现文件上传/下载
  - 基于 Milvus 索引做关键词检索/过滤
- 前端采用 Bootstrap 响应式设计，移动端使用底部固定输入框与 Viewport 适配。

## 原文精彩摘录

> 这不是个例。根据我对20位知识工作者的非正式调研，87%的人表示经常找不到已存储的文档内容，63%的人曾因“找不到”而重复下载或重新整理资料。传统文件系统与人类记忆之间的认知鸿沟，正成为知识利用率低下的首要原因。

> 至此，产品价值主张自然浮现：构建一个可随时随地从任何设备访问、支持多用户的云端AI知识库，让组织成员像聊天一样抽取文档精华。
